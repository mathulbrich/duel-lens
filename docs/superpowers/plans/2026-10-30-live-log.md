# Live Log Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** While a video plays, Duel Lens reads a few frames a second and lists every card it is sure of in the side panel's Live tab, without pausing the video.

**Architecture:** A content-script loop (`src/content/live/`) samples the video with `requestVideoFrameCallback`, watches 8×4 zones of a tiny grey thumbnail every 200 ms, runs the detector through a new background message `live-detect` (today's `detectCards`) when a zone settles after moving (or every 10 s), tracks boxes across detections, reads voting tracks with today's `recognize` (`record: false`) only while their zones are quiet (again from their last box, without the detector), and promotes a card after 2 agreeing confident reads. It reports one `live-progress` message per cycle; the background (`src/background/live.ts`) folds it into a `LiveLog` in `chrome.storage.session` key `live`, sets the badge and menu, and the side panel renders that log.

**Tech Stack:** TypeScript, Preact, MV3 (Chrome offscreen engine, Firefox event-page engine), ONNX Runtime Web, vitest + happy-dom, Puppeteer E2E.

**Spec:** `docs/superpowers/specs/2026-10-30-live-log-design.md` (decisions D-L1 to D-L12, the copy table). UI preview: artifact "Live Log Preview".

## Global Constraints

- Work on a branch `live-log` (worktree); commit per task; never push without the user's say-so.
- Never run plain `node build.mjs`: `dist/` is the user's installed build. Builds go to `--out` folders (the E2E scripts already do).
- Never load youtube.com (or any live site) in automation. Live-site checks are the user's, by hand.
- No new manifest permission and no new host. `npm run release`'s `verifyBuild` must stay green.
- Every new message key goes into all 9 locales (`en de es fr it ja ko pt_BR zh_CN`) with an `en` description; `src/shared/i18n.test.tsx` enforces it. Translations are written by the implementer, natural and short.
- A new `ToBackground` type needs a `BACKGROUND_SENDERS` entry (`src/shared/messages.ts:182`).
- A new `Settings` group must be added in both `fromStored` and `setSettings` (`src/background/settings.ts:68-75`, `:93-99`).
- Values are the spec's, verbatim: frame JPEG 0.85, long side 1280; efforts `balanced {load 0.2, minIntervalMs 500, slowAboveMs 2000}`, `light {load 0.1, minIntervalMs 2000, slowAboveMs 4000}`; max interval 8000 ms; slow after 3 cycles; gate 64×36 in 8×4 zones, sampled every 200 ms, zone quiet < 3, moving ≥ 6, settled after 2 quiet samples, cut ≥ 40 (whole frame) or a media-time jump over 2 s, refresh 10 000 ms; tracker IoU 0.3, miss limit 3 detections, min long side 0.045 of the video height, 2 reads per cycle; vote agree 2, read limit 4; log max 200 entries, reappearance gap 20 s, seek lead 3 s; badge `LIVE` `#C8322B`; shortcut `Alt+Shift+L`; storage key `live`.
- Frames and crops never leave the computer and are dropped after each frame (canvas width/height set to 0, as `capture.ts` does).
- English copy exactly as in the spec's copy table.

## Review Focus

1. YouTube moves to the next video (autoplay or a click) without reloading the page while Live runs: Live must stop with `stopReason: 'left'` and keep the list. (Task 5 test `stops when the page's video changes`.)
2. The engine is slow or stuck (a detect taking 5–30 s): there must never be a second `live-detect` in flight, and frames must not queue up. (Task 5 test `never sends a second frame while one is in flight`.)
3. The video is paused or the tab is hidden: no frames read, no messages sent, status `paused`; it resumes by itself. (Task 5 test `pauses with the video and the page`.)
4. A page with several videos (YouTube's hover previews, a picture-in-picture clip): Live must follow the largest visible video and not jump to a preview. (Task 4 test `pickLiveVideo prefers the largest visible playing video`.)
5. Live started where it can't work (no video, an unreadable DRM frame): the user gets a toast and the panel a status; nothing keeps running. (Task 5 tests `start answers no-video` and `stops as blocked on an unreadable frame`.)

The loop, per `requestVideoFrameCallback(now, metadata)` on the chosen video, while running, not paused and no scan open:
1. **Sample** at most every `GATE.sampleMs`: `thumbOf(video)` → `zones.sample`; `'cut'` → `tracker.reset()`. Also cut (`zones.cut()` + `tracker.reset()`) on a `seeking` event, a new `video.currentSrc`, or `|ΔmediaTime − Δnow × playbackRate| > LIVE.jumpS` between two samples. After a pause, `zones.rebase()`: the first sample compares nothing.
2. Return if a request is in flight or `now < dueAt`.
3. **Detect cycle** when `detectReason({ first, settled: zones.takeSettled(), sinceDetectMs })` is not null: grab (`grabVideoFrames`, the chosen video's); unreadable → `stop('blocked')`; encode (`LIVE.frameMaxSide`, `LIVE.frameQuality`); `live-detect`; `toNativeBoxes`; `tracker.update(boxes, video size)`; then reads of `tracker.toRead(may)`, where `may` is `zones.quiet(t.box)`, or always true when the reason is `'refresh'`.
4. Otherwise a **read cycle** when `tracker.toRead((t) => zones.quiet(t.box))` is not empty: grab and read those tracks from their last `card` box, without `live-detect`. Otherwise do nothing: no message.
5. Each read: `liveCrop` + `recognize` (`record: false`, `context` from the page and `metadata.mediaTime`), `readOf`, `settle`; newly promoted tracks become `sightings` with `videoTime = metadata.mediaTime`. `costMs` = the cycle's wall time; `dueAt = now + rate.next(costMs)`. Send one `live-progress` (`status` `'slow'` when `rate.slow`, else `'watching'`). Release canvases. Record `thumbMs`, `encodeMs` and `cropMs` in `stats`.

Status changes without a cycle (pause, play, visibility) send a `live-progress` with no sightings. `pageKey(location.href)` differing from the start's stops with `'left'`.
